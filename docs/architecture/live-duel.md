# Живая дуэль (фазы 13–14)

Два телефона одновременно проводят 60-секундный бой и видят аватар соперника, который в реальном времени повторяет его позу. Входов два:

- **«Найти соперника»** на главном экране — случайная очередь (`matchPlayers`). Двое, нажавшие поиск в одно время, встречаются в рейтинговой живой дуэли (режим `pvp`). Если за ~9 с никого нет — бой с лучшим сетом другого игрока, иначе со своим гостом (асинхронный путь остаётся основным при малом онлайне).
- **Бой с другом** по 6-значному коду — товарищеский, без трофеев и Aura.

Бой из очереди даёт трофеи `pvp` и Aura как обычная дуэль.

## SDK

**Photon Realtime** (`LoadBalancingClient`), который входит в пакет **PUN 2 FREE** из Asset Store. PhotonView, `PhotonNetwork` и `OnPhotonSerializeView` не используются: дуэль шлёт свои бинарные сообщения через `RaiseEvent`. Fusion не нужен: в дуэли 1×1 нет общей физики, у каждого телефона своя симуляция, а синхронизировать надо только старт, счёт и позу.

- Код транспорта: `Assets/_Project/Scripts/Photon/PhotonDuelTransport.cs`, сборка `PushStars.Photon`. Компилируется только с define `PUSHSTARS_PHOTON`.
- Define ставит и снимает `Editor/PhotonDefineSync.cs`: он смотрит, есть ли папка `Assets/Photon/PhotonRealtime`. Импорт PUN 2 — это и есть «включатель». Сборка без SDK собирается, а «Бой с другом» на устройстве честно отвечает, что приглашения недоступны.
- Конфиг: `Resources/LiveDuelConfig.json` — AppId (не секрет), **фиксированный регион** `eu` (комната находится по имени только внутри региона), версия протокола приложения, `customAuth`.

## Поток

```
Хост: INVITE ─► createLiveDuel ─► код 123 456 + matchId ─► Photon JoinOrCreate("pd_<matchId>")
Гость: код ─► peekLiveDuel (кто зовёт) ─► joinLiveDuel ─► Photon JoinOrCreate("pd_<matchId>")
Оба: STATE (имя, герой, пол, ready) раз в секунду ─► оба READY ─► у обоих открывается Fight
Fight: каждый встаёт в планку ─► STATE armed ─► хост назначает START = serverTime + 4000 мс
       ─► оба зовут startLiveDuel ─► 3-2-1 к одному и тому же моменту ─► 60 с
       поток: POSE 12 Гц (unreliable), SCORE при каждом репе (reliable)
Финиш: экран результата сразу, по счёту, который оба телефона видели вживую;
       свой таймлайн уходит в finishLiveDuel в фоне (до 6 попыток) ─► сервер сравнивает оба
```

### Очередь (кнопка «Найти соперника»)

```
Поиск ─► enqueueLiveDuel ─► waiting ─► pollLiveDuel раз в 1 с (до 9 с)
   кто-то уже ждёт / нашёл нас ─► matched {matchId, host?, имя/герой соперника}
        ─► Photon pd_<matchId> ─► оба в комнате ─► OPPONENT FOUND ─► FightPreparation
        ─► карточки обоих + READY ─► READY нажали оба ─► Fight (сет как в бою с другом)
   9 с никого ─► leaveLiveDuel ─► {left, ghost: лучший сет чужого игрока из сезона | null}
        ─► гост чужого игрока ─► иначе свой гост ─► иначе сначала замер
```

- Логика поиска — `UI/Duel/LiveQueueSearch.cs` (машина состояний, тикается экраном поиска; сеть — через `ILiveQueue`, в приложении это сервер, в регрессии — очередь в памяти). Экран — `SearchOpponentController`, UI не менялся: то же кольцо, та же карточка «OPPONENT FOUND».
- Хостом (назначает общий старт) становится тот, кто ждал; нашедший — гость.
- Экран подготовки (`PreparationScreen`) для живого боя — проверка готовности: карточка соперника (имя, флаг, его герой на стенде), READY отправляет флаг ready в комнату, кнопка пишет WAITING…, бой открывается у обоих, когда ready оба. Соперник ушёл, сменил версию или не нажал READY за 40 с — комната закрывается, матч отменяется, игрок возвращается на главный экран. «Домой» делает то же.
- Пара найдена, но соперник не пришёл в комнату за 10 с, ушёл (BYE) или у него другая версия протокола — матч отменяется (`cancelLiveDuel`), поиск заканчивается фолбэком.
- Отмена неначатого матча из очереди удаляет оба места в очереди: телефон, который ещё не узнал о паре, на следующем poll просто продолжает искать, а не ждёт в пустой комнате.
- «ВЫЙТИ» во время поиска освобождает место (`leaveLiveDuel`) или выходит из комнаты и отменяет матч.
- Нет сети / сервер не отвечает на enqueue — сразу фолбэк. Потерянный poll не прерывает поиск (место живёт 5 с).
- Без Photon в сборке (`LiveDuelService.Available == false`) — как раньше: 2,5 с и свой гост.
- Гост чужого игрока: таблица текущего сезона (`seasons/{id}/players`, `bestTimes` из рейтинговых сетов), из трёх ближайших по репам к лучшему сету игрока — случайный. Бой как со своим гостом (журнал `ghost`, трофеи ghost), под именем того игрока; на экране подготовки — его имя и репы.

## Протокол (`Core/LiveDuel`)

| Код | Сообщение | Канал | Содержимое |
|-----|-----------|-------|------------|
| 1 | STATE | reliable | версия протокола, uid, имя, страна, герой, пол, флаги ready/armed/finished, итоговые репы. Раз в секунду — это и heartbeat |
| 2 | START | reliable | момент старта по серверным часам Photon (мс). Шлёт только хост; первое значение окончательное |
| 3 | SCORE | reliable | репы, хлопки, FORM, секунда сета. Счёт только растёт |
| 4 | POSE | unreliable | кадр `GhostMotionClip.Frame`: 95 мышц Humanoid в int16 и root/body. 236 байт, около 2,8 КБ/с |
| 5 | BYE | reliable | ухожу сам |

- `LiveDuelLink` — логика комнаты поверх любого `IDuelTransport`; через `LiveDuelLink.Active` + `LiveDuelRunner` переживает смену сцен.
- `LivePoseCodec` / `LivePoseBuffer` — те же позы, что пишут гост-записи (`FightPoseRecorder`), в виде скользящего клипа; проигрываются через `GhostPosePlayback` с задержкой 0,2 с.
- Соперник в бою — `Fight/LiveOpponent.cs`: `IOpponentFeed` (счёт) + `IOpponentPose` (тело). `GhostAvatarDriver.Follow` переключает аватар соперника на него, поэтому сцену боя менять не нужно.

## Диагностика зависаний

`Core/LiveDuel/LiveDuelDiagnostics.cs`. Пока открыта живая комната, фоновый таймер следит за главным потоком (его «пульс» — `LiveDuelRunner.Update`). Если главный поток стоит больше 8 с, в `persistentDataPath/live-duel-hang.txt` пишется последний шаг боя (`search:room`, `prep`, `prep:ready`, `fight:open`, `fight:countdown`, `fight:set-begin`, `fight:set me N peer M @Ts`, `fight:finish`), сцена и сколько секунд прошло с шага. Если поток ожил меньше чем через 20 с (медленная загрузка сцены), запись стирается. При следующем запуске она уходит в PostHog событием `live_duel_hang`.

**Зависание 2026-10-20 (оба iPhone, после первого повтора) — причина найдена.** `LiveOpponent.Tick` догонял счёт так: `while (Reps < PeerReps) OnRep?.Invoke(++Reps);`. При `OnRep == null` оператор `?.` пропускает вызов вместе с аргументом, `++Reps` не выполняется, цикл вечный. На повторы живого соперника никто не подписан, поэтому первый же его повтор вешал главный поток. Теперь сначала счёт, потом событие; регрессия проверяет догон без подписчиков. Найдено воспроизведением в редакторе (см. ниже): сторож записал последний шаг `opp:loop`.

Попутно: фоновый keep-alive `PhotonDuelTransport` больше не трогает peer одновременно с главным потоком (`_peerLock`, таймер только `Monitor.TryEnter`).

## Поза соперника

Сцена игрока двигает и масштабирует собственный риг под свой кадр (в подготовке и сете корень уходит, например, в (1,66; −1,74) с масштабом 4,14). `HumanPoseHandler.GetHumanPose` отдаёт `bodyPosition` с этим сдвигом. Раньше получатель применял и присланный корень, и тело: соперник «плавал» в подготовке и улетал из кадра со стартом сета. Теперь `FightPoseRecorder` снимает позу для потока так, будто риг стоит в покое (корень в нуле, без поворота, масштаб при привязке), а `GhostPosePlayback` держит корень живого соперника на месте и кадрирует его сам. Записи гостов снимаются и проигрываются по-прежнему.

## Бой целиком в редакторе

`Tools ▸ Push Stars ▸ Live Duel ▸ Play Live Fight (Loopback)` (`Editor/LiveFightPlayTest.cs`): сцена Fight с живой связью через `LoopbackDuelTransport`. Соперник — второй `LiveDuelLink`, которым управляет инструмент: назначает общий старт, пересылает позы самого игрока (как настоящий второй телефон), набирает повтор каждые 1,5 с. Повторы игрока подаются через событие сессии (фейковый источник позы планку не держит). Раз в секунду пишет состояние в `Logs/live-fight-play.txt`, снимки обеих сцен — в `output/live-fight/`. Работает и в batch-режиме, когда редактор закрыт:

`Unity.exe -batchmode -projectPath "D:/Push Stars" -executeMethod PushStars.Editor.LiveFightPlayTest.Run -logFile Logs/live-fight-batch.log` (без `-quit`; процесс потом закрыть).

## Разрыв связи

- Соперник считается **отошедшим**, если Photon говорит, что его нет в комнате, **или** от него 3 с нет ни одного сообщения (зависший телефон «до свидания» не скажет).
- Отошёл на **10 с** (окно реконнекта, `PlayerTtl` комнаты) — **ушёл**. В бою сет заканчивается досрочно, это walkover; до старта бой отменяется.
- Пока **этот** телефон сам офлайн, соперника не судим. Свои репы продолжают считаться, результат уйдёт по HTTPS.
- Транспорт переподключается через `ReconnectAndRejoin` каждые 2 с, через 25 с сдаётся.
- Уход после финального гонга (флаг FINISHED приходит раньше BYE) поражением не считается.

## Сервер (`functions/src/liveDuel.js`, правила — `liveDuelRules.js`)

| Функция | Что делает |
|---------|------------|
| `createLiveDuel` | код (5 мин) + `liveDuels/{matchId}`; имя хоста берётся из профиля, а не от клиента |
| `peekLiveDuel` / `joinLiveDuel` | своя ссылка, полная комната, истёкший или чужой код |
| `cancelLiveDuel` | хост ушёл до старта — код освобождается; матч из очереди — освобождаются оба места |
| `enqueueLiveDuel` / `pollLiveDuel` | очередь: встать / держать место (heartbeat 5 с) и составить пару в транзакции; `liveDuels/{matchId}` с `mode: 'pvp'`, без кода |
| `leaveLiveDuel` | выйти из очереди; пара, составленная в последний момент, остаётся в силе; иначе — гост чужого игрока |
| `startLiveDuel` | время старта для проверки «слишком рано»; код сгорает |
| `finishLiveDuel` | таймлайн игрока (правила как у ranked: ≤65, шаг ≥0,4 с, полная минута, если соперник не ушёл) |
| `onMatchFinished` | вебхук Photon с `X-Photon-Token`: Join / Leave / Close → `liveDuels/{id}.room` |
| `photonAuth` | кастомная авторизация Photon: Firebase ID token → `UserId = uid` |
| `cleanupMatchmaking` | каждые 5 мин: истёкшие коды и неначатые матчи очереди (90 с); дуэли, где результат так и не пришёл; брошенные места в `liveDuelQueue` |

**Античит.** Репы игрока = его собственный таймлайн, но не больше, чем соперник видел вживую, + 3 (если оба оставались на связи). Телефон не может стримить 20 и сдать 50 — такие репы режутся, а матч помечается флагом `capped:<uid>`. Walkover засчитывается только при доказательстве: Photon записал уход соперника **до гонга** без последующего rejoin, или соперник не прислал результат до дедлайна (старт + 64 с + 120 с). Если оба потеряли друг друга (разрыв сети между ними), побеждает тот, у кого больше репов, а не тот, кто первым пожаловался.

**Очередь в Firestore.** `liveDuelQueue/{uid}` — одно место на игрока. Ждущее место видно другим только пока телефон опрашивает (`waitUntilMs`, один range-запрос без составного индекса). Пара составляется в транзакции, которая читает оба места, поэтому два телефона, одновременно нашедшие друг друга, создают один матч. Новый поиск не наследует пару старше 5 с (брошенный поиск).

**Трофеи и Aura.** `LIVE_DUEL_TROPHIES` в `constants.js`: бой с другом — 0/0 (лист комнаты обещает «No trophies»), очередь `pvp` — ±25/15, сервер пишет их в профиль. Локально бой с другом пишется в журнал с режимом `friend` (без трофеев и Aura — иначе два друга могли бы по очереди сдавать друг другу бои), бой из очереди — с режимом `pvp` (трофеи ±25/15 + бонус серии, как у локального pvp). Бой из очереди — это основная дуэль приложения, поэтому Aura за него начисляется как за любую дуэль (`AuraCalculator.ForFight`, решение владельца 2026-10-20). Победа, ничья и репы соперника для Aura берутся из вердикта сервера.
